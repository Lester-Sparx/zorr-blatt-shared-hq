## A2. Windows-safe Task invocation — supersedes Task 2 command examples

The base plan examples interpolated shell-style `$ZB_*` path variables inside Task commands. That is not sufficiently shell-neutral for Windows and creates unnecessary quoting surface.

Replace the Task command examples with static commands only:

```yaml
version: '3'

tasks:
  zb:exec:lester:implement-r01:
    cmds:
      - cmd: python scripts/zb_execution_cli.py execute --from-env
        timeout: 30m

  zb:exec:duncan:qc-r01:
    cmds:
      - cmd: python scripts/zb_execution_cli.py qc --from-env
        timeout: 15m
```

The Python entrypoint reads only these exact trusted environment variable names:

```text
ZB_EXECUTION_REQUEST_PATH
ZB_EXECUTION_RESULT_PATH
ZB_EVIDENCE_DIR
ZB_CANDIDATE_EVIDENCE_DIR
ZB_QC_RESULT_PATH
ZB_EXECUTION_ID
ZB_WORKFLOW_RUN_ID
ZB_WORKFLOW_RUN_ATTEMPT
```

Rules:

- values are generated by trusted workflow/adapters after request validation, not copied raw from GitHub message text;
- the CLI canonicalizes each path and requires it to remain under the current job workspace/evidence root;
- Task receives no arbitrary positional arguments and no `CLI_ARGS`;
- Task never expands a GitHub-provided executable name, command fragment, profile name, model, or checkout ref.

Task 5 CLI surfaces are therefore superseded by:

```text
python scripts/zb_execution_cli.py execute --from-env
python scripts/zb_execution_cli.py qc --from-env
python scripts/zb_execution_preflight.py --mode implementation
python scripts/zb_execution_preflight.py --mode activation
```

Direct Python functions remain injectable in unit/integration tests; `--from-env` is the production Task boundary.

## A4. OpenCode documented headless argv — supersedes Task 4 argv

Do not use unverified `--auto`, `--pure`, or `--dir` flags in the R01 `opencode run` adapter.

The first adapter uses only documented `run` flags:

```python
[
    "opencode",
    "run",
    "--format", "json",
    "--agent", "build",
    prompt,
]
```

The process runner sets `cwd=worktree`; it does not pass a path through an OpenCode CLI flag.

The prompt is derived deterministically from trusted normalized request fields and must state the write-scope, no-commit/no-push/no-merge law, required tests, and result expectations. GitHub message text cannot choose the binary, agent name, model, flags, tools, or permission policy.

## A5. OpenCode output is diagnostic evidence, never PASS authority

Current upstream history includes headless/JSON-output bugs where `opencode run` may emit incomplete or empty JSON output while side effects occur. Therefore:

- `worker-events.jsonl` is retained as diagnostic evidence when emitted;
- missing/incomplete final JSON event does **not** itself become PASS or FAIL authority;
- process exit code is recorded but is not sufficient for PASS;
- actual filesystem diff, Git HEAD, changed-file allowlist, required verification commands, evidence manifest hashes, and independent DUNCAN recomputation remain authoritative;
- a worker process that cannot be proven to have started/finished maps truthfully to `EXECUTION_ERROR` or `BLOCKED`, never synthetic PASS.

This keeps ZB correctness independent from one worker CLI's stdout stability.

## A6. Effective OpenCode configuration preflight — supersedes simple config-file assumption

OpenCode merges multiple configuration sources. `OPENCODE_CONFIG` alone is not a complete isolation boundary because later project/config-directory sources may override or add behavior.

R01 activation therefore requires all of the following:

1. run the self-hosted execution service under a dedicated low-privilege OS account whose OpenCode user configuration is controlled for ZB execution;
2. reject execution worktrees containing any of:
   - `opencode.json`
   - `opencode.jsonc`
   - `.opencode/`
3. set the static ZB config path/directory from trusted host policy, not request fields;
4. disable auto-update/share in the static policy;
5. run `opencode debug config` before worker execution and parse the resolved explicit configuration;
6. fail closed if resolved config contains an unapproved MCP server, plugin, command/agent override, sharing policy, external-directory permission, or shell permission wider than the R01 allowlist;
7. fail closed if an unexpected managed/global config source is detected or the effective policy cannot be verified;
8. strip GitHub repository credentials/OIDC variables from the worker environment as already required by the base plan.

The effective-config preflight is tested with safe and malicious fixtures. The worker is not allowed to self-modify its policy.

## A7. Worker backend remains optional and replaceable

OpenCode is the first **candidate** LESTER coding worker, not ZB contract authority. `WorkerPort` remains backend-neutral. If implementation-time verification finds a blocking OpenCode regression, R01 may use a separately pinned Codex CLI adapter or another OWNER-approved OSS worker without changing `ZB_EXECUTION_REQUEST_V1`, `ZB_EXECUTION_RESULT_V1`, Task profile authority, artifact/evidence law, DUNCAN QC, or OWNER gate.

Such a backend switch is a dependency/profile authority change and must be recorded with exact version/provenance before use; it is not a GitHub-message choice.
